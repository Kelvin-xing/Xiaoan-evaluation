# 小安内容撰写指南

本指南适用于负责撰写或修改小安场景胶囊、系统提示词、Baseline SOP、Crisis SOP、
安全规则和其他对话内容的人与大模型。

## 一、先理解：Prompt 不是工具箱

- **Chatflow** 像一条预先设计的流水线，每一步由后端决定。
- **Agent** 可以在运行时决定下一步，但也只能调用后端已经注册给它的工具。
- **Prompt、SOP 和胶囊**是工作说明，不会因为写入一句话就让系统获得新能力。

给说明书写一句“需要时联系真人”，不会让系统凭空拥有电话、联系人或转接能力。
即使改用 Agent SDK，也必须先实现并注册真正的工具、权限、状态和失败处理。

## 二、小安当前的真实 Chatflow

```text
用户消息
  ↓
安全分类 LLM
  ├─ CRISIS                 → Crisis SOP
  ├─ UNCLEAR / 分类调用失败 → 后端固定安全澄清问题
  └─ NO_IMMEDIATE_CRISIS    → Router 选择恰好一个胶囊
                              ↓
                    Ground 条件分支与来源角色筛选
                              ↓
                  回答模型根据已选内容生成回复
                              ↓
                          Output Guard
```

当前回答模型：

- 只收到编排层已经选中的一个胶囊，以及本轮命中 Ground 分支所解析出的来源片段；
- 看不到完整胶囊目录或其他胶囊内容；
- 不能自行加载、调用、切换或跳转到 N2、N5p、NC 等其他胶囊；
- 不能修改 Router 的选择或自行建立跨轮 Crisis 状态；
- 不能主动追发消息、替用户报警、联系机构或转接真人；
- 不具备任何未由后端明确实现并注册的工具能力。

因此，在胶囊里写“发现威胁后转向 N2”，不会让系统真的转向 N2。它只是一句无法执行的文案。

## 三、不是每个需求都需要 Function Call

但每个需求都必须有一个真正负责执行它的组件。撰写前先把每条拟新增规则分为以下五类：

| 分类 | 含义 | 示例 | 可以直接写进 Prompt/胶囊吗 |
|---|---|---|---|
| `TEXT_ONLY` | 回答模型在当前轮通过文字即可完成 | 语气平稳；最多问两个问题；不编造法条 | 可以 |
| `ROUTER` | 需要前置路由或重新选择内容 | 转向 N2；加载保护令胶囊；进入 Crisis SOP | 不可以 |
| `STATE` | 需要保存并读取跨轮状态 | 首次进入时提醒；连续两轮安全后退出；不要重复建议 | 不可以 |
| `TOOL` | 需要 Function/API 或外部系统执行 | 查询附近机构；发送短信；预约；联系真人 | 不可以 |
| `UNSUPPORTED` | 当前系统尚无负责组件 | 十分钟后主动跟进；自动监控用户是否安全 | 不可以 |

**只有 `TEXT_ONLY` 可以直接写成可执行的 Prompt、SOP 或胶囊指令。**

`ROUTER`、`STATE`、`TOOL` 和 `UNSUPPORTED` 应记录为运行时产品需求，不能伪装成现有能力。

## 四、哪些内容可以直接写

只涉及“当前这次回复如何表达”的要求，例如：

- 使用平稳、不评判的语气；
- 不责怪用户，不替用户作决定；
- 普通回复最多问两个问题；
- 不编造本轮没有提供的法律依据；
- 用户主要在倾诉时，先回应其处境，不抢着给方案；
- 使用本轮输入中已经提供并经过核验的资源信息；
- 按当前胶囊已经提供的 `recognize`、`act` 和 `ground` 组织回复。

## 五、哪些内容不能只靠文案实现

### 1. 需要 Router 或编排层

例如：

- “转向 N2”
- “调用 N5p”
- “同时加载安全计划”
- “中止 K3，进入 Crisis”

这些动作发生在回答模型运行之前，必须由 Router、安全分类器或其他后端编排代码执行。

### 2. 需要跨轮状态

例如：

- “首次进入本胶囊时提醒一次”
- “用户已确认安全则不再重复”
- “连续两轮安全后退出 Crisis”
- “记住用户此前拒绝过报警”
- “反复命中时换一种策略”

这些要求必须有明确的状态字段、写入时机、读取逻辑、退出条件和自动化测试。

### 3. 需要 Function/API

例如：

- 查询热线当前是否可用；
- 查找用户附近的服务机构；
- 联系人工客服或专业人员；
- 替用户发送短信、报警或创建预约；
- 在未来某个时间主动跟进。

这些能力需要真实的 Function/API、权限和用户同意，还必须处理输入校验、失败、超时、
隐私、审计和测试。Prompt 本身不能完成这些动作。

## 六、胶囊字段的当前职责

- `triggers`：供 Router 召回候选胶囊。
- `use_when`：供 Router 判断本胶囊何时适用。
- `do_not_use_when`：只写本胶囊不适用的条件，不写目标胶囊或执行动作。
- `render_policy`：只填写回答模型在当前轮如何选择、组织和表达已提供素材的约束，不负责加载 `ground`。
- `recognize`：填写认知素材；已有 Markdown 子标题和分组必须保留。
- `act`：填写本轮行动素材，可使用 Markdown 子标题表达阶段或选项；`scripts` 是其可选子分区。不得把这些层级压成单层步骤列表。
- `ground`：使用 `if + node + source_roles` 描述本轮何时展开哪个 wiki 节点的哪些来源角色；
  三个字段必须同级，不得增加同义字段。来源角色由知识库方法定义，胶囊不得恢复
  `legal_basis` / `practice_basis` 二分法。
- `related_capsules`：仅供编辑者理解内容关系，不参与运行时路由。

## 七、看到这些词时先停止写作

如果拟新增规则包含以下词语，先不要把它直接写进 Prompt 或胶囊：

- 记住、首次、以后、连续几轮、反复；
- 自动、定时、稍后、主动跟进；
- 加载、调用、切换、跳转、转向；
- 查询、联系、转接、发送、预约、报警；
- 监控、进入状态、退出状态。

先判断它属于 `ROUTER`、`STATE`、`TOOL` 还是 `UNSUPPORTED`。

## 八、运行时需求的正确写法

如果需求不是 `TEXT_ONLY`，不要把它写成模型已经能够执行的命令。应单独记录为运行时需求，并回答：

1. 哪个组件负责执行？
2. 当前代码是否已经实现？
3. 需要读取或保存什么状态？
4. 是否需要 Function/API、权限或用户确认？
5. 失败、超时或结果不确定时如何处理？
6. 用什么自动化测试证明它真的生效？

如果这些问题没有答案，该需求只能标记为 `UNSUPPORTED` 或待实现，不能写成现有行为。

## 九、提交前检查

- [ ] 每条新增规则都已标记为 `TEXT_ONLY`、`ROUTER`、`STATE`、`TOOL` 或 `UNSUPPORTED`。
- [ ] 只有 `TEXT_ONLY` 被写进了 Prompt、SOP 或胶囊的可执行指令。
- [ ] 没有暗示回答模型能看到完整胶囊目录。
- [ ] 没有在普通胶囊中写跨胶囊调用或 Crisis 状态切换。
- [ ] 没有用文案模拟首次进入、连续轮次、去重或主动追发。
- [ ] 所有热线、机构、法律和服务能力都有可靠来源，未核实内容明确标注待核实。
- [ ] 所有运行时需求都指出了负责组件、实现状态和测试。

## 核心原则

> Prompt 负责“怎么说”；Router 负责“用哪个胶囊”；状态机负责“跨轮记住什么”；
> Function/API 负责“真正做什么”。
