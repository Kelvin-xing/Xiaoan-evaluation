# 小安 source 文件处理规范

> 面向：负责整理 `content/knowledge/source/` 原始资料的同事及其 AI 助手。
> 新资料按本文的标题路径规则整理；程序提供显式严格模式验收。旧资料迁移完成前，现有运行时暂保兼容模式，不能把兼容模式通过当作新规范验收通过。

## 目录结构

原始资料全部平铺在一个目录下，不再按法源分子目录：

```
content/knowledge/source/
├── 目录.md              ← 人工核对资料完整性的清单，必须保留，不作为正文来源抽取
├── source-文件处理规范.md
├── 001-宪法.md
├── 002-中华人民共和国反家庭暴力法.md
└── …                    ← 其余按编号平铺
```

**分类只由 frontmatter 的 `source_code` 表达，目录不承载分类判断。**
过去按 `legal/`（A–I）和 `practice/`（J–K）分目录的做法已取消：目录一旦编码分类，
律师重新定 code（例如 canonical 080／legacy-82 在 H/K 之间）就要搬文件、改所有引用，既脆弱又会把 G、H、I
误读成有对外法律效力。分类信息一律写进 frontmatter；`source_ref` 使用
`knowledge/source/NNN-名称.md#标题路径`，每个 source 只有一条规范路径。

`source_code` 必须由人根据发布主体、法律效力和材料性质判断，不能从文件名反推。
发布主体相同也不保证代码相同，例如妇联以法定身份发布的规范或官方实务材料可归 G–I，
政策解读、学说或监测材料可归 K。

`source/` 是知识库的来源资料库，不是只收录法律条文的法规库。国际材料、政策解读、
实务手册、案例汇编、监测报告、学说和说明性材料都可以作为 source；其法律效力和使用
边界由 `source_code`、`source_tier`、发布主体和正文共同表达。不得仅因一段内容不是
法律原文就将其删除。

⚠️ 两个容易混淆的同名陷阱：

| 名字相似 | 归 A–I（正式法源／官方材料） | 归 J–K（国际／非正式） |
| --- | --- | --- |
| 「实务手册」 | 国家机关发布且归 I 的办案手册／执法指引 | 归 K 的 NGO 手册、经验材料或非正式法源 |
| 「案例」 | 归 H 的指导性、典型或裁判文书 | 归 K 的监测案例汇编 |

区分靠经人工确认的**材料性质与法源代码**，不靠名字或目录。
当前 canonical source 080（legacy-82）《反家庭暴力典型案例选编》已经人工确认为 K/3；不得仅凭“全国妇联”
或“典型案例”字样自动改归 H 或 I。

## 重建风险清单（持久化）

本清单是 source 治理元数据，不是发布机构原文，也不能作为 Wiki 主张的证据。它必须留在
生成目录 `content/knowledge/wiki/` 之外。开始全量重建或增量 ingest 前，agent 必须把每个
未解决的 `risk_id`、状态、影响范围和处理限制复制到新的 `source-registry.md`；不能依赖
GitHub Issue、旧 Wiki 或 session history 才知道这些风险。

风险状态：

- `TEXT_BLOCKED`：受影响 passage 修复并核验前，不得生成节点、边、综合或运行时摘录。
- `PROVENANCE_REVIEW`：来源或段落归属未确认；不得把内容归因给 frontmatter 中的机构。
- `LEGAL_REVIEW`：现行性或法律结论待律师判断；不得作为当前规则或 `legal_basis`。
- `SELECTIVE_ONLY`：source 留库，但只能抽取表中允许的独特内容，不能整篇进入 Wiki 或运行时。

一个 source 可以同时有多种状态。风险只阻断表中列明的范围，不自动否定同文件内其他已核验
passage。风险关闭并完成核验后，从本清单删除；本清单只保留仍会影响抽取、归因或法律判断的
开放风险，不把已解决事项继续复制到新的 `source-registry.md`。

## 背景：为什么格式如此重要

程序不会把整份文件喂给模型，而是按 `文件路径#锚点` 去原文里**搜索并截取片段**，例如：

```
knowledge/source/002-中华人民共和国反家庭暴力法.md#第四章 人身安全保护令/第二十三条
```

这里的 `knowledge/source/` 是 source_ref 的稳定逻辑前缀；仓库中的物理目录是
`content/knowledge/source/`。存储引用时不要额外添加 `content/`。

严格模式按标题路径找到 `### 第二十三条`，从该标题读到下一个同级或更高级标题之前。它不识别“法条特例”，也不固定截取若干行。

所以一份文件能不能用，取决于**能否被准确切片**，而不只是能不能打开。

## Q1：没有乱码就够了吗？

**不够。** UTF-8、无乱码只是「能读」，不等于「能用」。

必须同时满足两条：

| 要求 | 说明 |
| --- | --- |
| **① 保留语义边界** | 标题独占一行，正文按自然段保留；不要把标题与前后正文挤到同一行，也不要整页压成一行 |
| **② 标题路径唯一** | 标题可在不同父级下重名；完整路径必须能唯一定位 |

**反例（真实文件）**：某手册无乱码、UTF-8 干净，但全文仅 137 行、最长一行 4124 字符，导致「危险评估」和「出警」两个不同锚点抽出**完全相同的 7381 字符**，整份文件等于报废。

**同名冲突处理**：不同年份下可以各有「案例一」，引用用 `2024年11月/案例一`；不同文件的法条可用 `法释〔2022〕17号/第六条`。各段必须是原文中真实存在的标题，不能把上下文直接拼成一个不存在的标题。

GitHub 的视觉折行不影响抽取。真实换行也不必一律合并；只修复确定的句中断行，不能合并本来独立的段落、清单或表格行。

## Q2：URL 和图片怎么处理

### URL —— 不要留在正文，放进文件头的 frontmatter

**为什么**：`---` 之间的内容不参与锚点搜索，不会被抽进片段；而写在正文里的 URL **有可能被抽进去，并出现在给用户的回答里**（已实测复现）。

- ❌ 正文第一行写 `source: https://...`
- ❌ URL 和法条写在同一行
- ✅ 统一放进 frontmatter 的 `url:` 字段

### 图片 —— 转成文字，否则删除

> **规则：图片里的内容 = 不存在。**

程序只读文本，`![](x.png)` 对模型是空白。

- **量表、流程图、表格**等关键内容若只以图片存在 → **必须人工转成文字**
- 装饰性、无信息量的图片 → **直接删除**，不要留下空标记

## Q3：标题层级要统一吗

**同级结构用同级标题，不是所有标题都用同一级。**

| 结构 | 写法示例 | 严格模式截取边界 |
| --- | --- | --- |
| 文件 | `# 文件标题` | 到下一个一级标题或文件末尾 |
| 章／大部分 | `## 第四章 人身安全保护令` | 到下一个二级或一级标题 |
| 条／案例／小节 | `### 第二十三条` | 到下一个三级、二级或一级标题 |

**混用会出错**：若「第二十三条」用 `#`、「第二十四条」用 `##`，程序**不会**在二十四条停下（因为 `##` 比 `#` 低级），会把它一起吞掉。

`一、二、三……` 不必叫“章节”，但如果是需要独立抽取的正式编号单元，也应加标题。普通段内枚举和法条引用不因此变成标题；不要机械地给所有编号加 `#`。

## 文件模板

### 正式法源／官方材料（A–I）示例

```markdown
---
source_code: B
source_tier: 1
official_title: 中华人民共和国反家庭暴力法
issuer: 全国人民代表大会常务委员会
effective_year: 2016
url: https://www.spp.gov.cn/zdgz/201512/t20151228_109929.shtml
---

# 中华人民共和国反家庭暴力法

## 第一章 总则

### 第一条

为了预防和制止家庭暴力，保护家庭成员的合法权益……

### 第二条

本法所称家庭暴力，是指家庭成员之间以殴打、捆绑……

## 第四章 人身安全保护令

### 第二十三条

当事人因遭受家庭暴力或者面临家庭暴力的现实危险……
```

以上只是节选格式示意，不是完整法条文本。正式文件保留原文，不补写或概括正文。
解读、报告、说明等非法律条文同样可以作为 source，并保留其自身内容；不得把它们
改写成法律原文，也不得仅因其没有法律效力而删除。

### 国际／非正式资料（J–K）示例

```markdown
---
source_code: K
source_tier: 3
official_title: 工作手册
issuer: 源众家庭与社区发展服务中心
url: https://...
---

# 工作手册

## 一、强制报告的适用情形

……
```

J–K 材料必须保留经人工确认的 `source_code` 和
`source_tier: 3`。资料平铺存放，路径不表示这些文件没有法源分类。

### frontmatter 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `source_code` | ✅ | 法源分类 A–K，见下表；分类只写在 frontmatter，不再对应子目录 |
| `source_tier` | ✅ | 法源层级 1–3，由 `source_code` 决定，见下表 |
| `official_title` | ✅ | 经原件核验的正式标题；不用于制造原文中不存在的正文标题 |
| `issuer` | ✅ | 发布机构；尚未确认时必须进入人工审查，不能猜测 |
| `effective_year` | 有则填 | 资料本身明确记载的施行或生效年份。使用四位整数，不写入文件名；修订、发布、通过、批准、出版或资料年份不能代填 |
| `url` | 有则填 | 官方原文链接；没有就不写 |
| `notes` | 有则填 | 整理者备注的字符串列表，必须放在其他字段之后；用于记录时效、出处或处理说明，不属于发布机构原文，也不能作为 Wiki 主张的证据 |

**不要为了填字段去满世界找信息**——文件本来就带的元数据搬进来即可，没有就留空。
正文中原有的制定、通过、发布、生效、更新和修订时间全部保留；`effective_year` 不替代这些版本
沿革。只删除整理过程重复添加的 `> **文档名称**`、`> **生效年份**` 等展示块。
整理者添加的时效、出处或处理说明不得混入正文；确需保留时写入 `notes` 列表，并明确标为
整理说明。`notes` 不参与正文抽取，不得借此把未经核验的判断变成 source 事实。

`source_code` 必须由人判断（律师为准），不要让程序猜。

### source_code 与 source_tier 取值

| 代码 | 类别 | tier |
| --- | --- | --- |
| A | 宪法 | 1 |
| B | 法律 | 1 |
| C | 行政法规 | 1 |
| D | 地方性法规、自治条例、经济特区法规等 | 1 |
| E | 部门规章、地方政府规章 | 1 |
| F | 司法解释 | 1 |
| G | 规范性文件 | 2 |
| H | 案例（指导性、典型、裁判文书） | 2 |
| I | 官方实务材料（办案手册、执法指引） | 2 |
| J | 国际条约与惯例 | 3 |
| K | 非正式法源与资料（政策、解读、案例汇编、监测报告、经验材料、习惯、法理、学说等） | 3 |

`source_tier` 完全由 `source_code` 决定（A–F→1，G–I→2，J–K→3），照表填即可，不要自行判断。

`source_code` 还是下游 Wiki 判定法律效力（effect）与证据角色（source_roles）的输入。
效力与角色写在 Wiki 节点，不写进 source frontmatter；`wiki/nodes/` 只收 A–F 承重的现行规则，
G/H/I/J/K 只作解读、机关实施、案例或实证挂靠，不能单独支撑节点，详见
`content/knowledge/AGENTS.md`。

⚠️ **I 类只给国家机关发布的官方实务材料。** NGO、民间组织的工作手册或监测材料
如经人工确认为非正式法源，归 K，并保留 K/3 元数据。

## 三条格式规则

### 规则 1：可独立抽取的结构单元用 Markdown 标题

章、条、案例、问答、小节等按原文结构加 `#`，标题必须独占一行。法条不再例外；原先“法条禁止加 `#`”的要求撤销。

```markdown
# 文件标题
## 第一章 总则
### 第一条
正文……
### 第二条
正文……
```

### 规则 2：保留父子层级，用路径区分重名

同级结构用同级标题，子项用更低级标题或保留正文。不能为了程序制造虚假的章节。

重复的「案例一」「条文主旨」不需要全文件改名。引用用连续的父级路径，例如 `2024年11月/案例一`、`第一条/条文主旨`；如果仍重名，就补足更上层标题。

严格模式按标题文字精确匹配，不做模糊包含匹配。唯一短标题可单独引用；父级路径可以省略文件总标题，但不能跳过中间父级。路径各段用 `/` 分隔，标题中的其他标点和内部空格应与原文一致。

> ⚠️ **禁止把原文的半角引号（`"` `'`）"美化"成全角/弯引号（`“` `”` `‘` `’` `＂` `＇`），反之也不行。** 这不是排版偏好，会造成两类真实故障：
> 1. **标题精确匹配失效**：如果引号出现在标题文字里，严格模式要求逐字符相等；改了引号，wiki 节点里已经写好的 `source_refs` 锚点就找不到对应标题，抽取直接报错（`heading path not found`）。旧的模糊匹配同样会失配，因为归一化只剥离半角引号，不认全角/弯引号。
> 2. **frontmatter 解析被破坏**：`title`、`official_title`、`source_refs` 等字段用英文半角双引号做 YAML 的字符串定界符，不是普通标点。把这层引号换成全角/弯引号后，YAML 会把它们当成普通文字保留在解析出的字符串里（而不是去掉），导致标题多出杂字符、`source_refs` 路径对不上文件名，抽取同样会报错或静默取不到内容。
> 如果同事的 AI 工具默认会做全角化处理，请在写入前人工核对一次半角/全角引号是否被改动；已经改过的文件要改回原文引号再提交。

### 规则 3：保留编号和 `目录.md`，目录条目不冒充正文标题

- 文件名前的编号、用于人工核对完整性的 `目录.md` **必须保留**。扫描程序不把 `目录.md` 计为正文来源。
- 文件内部目录可以保留供人工核对。目录段可以有自己的标题，但其条目用普通文本或列表，不重复建立正文标题树。
- 正文章节、条文按前两条处理；目录条目不作为知识引用锚点。

### 附：缩进与标题语法

正文不保留行首全角缩进；同一结构单元内仍按原文保留自然段（包括法条各款），自然段之间留一个空行。空行只表示段落边界，不会把一个法条切成多个抽取片段。**标题应顶格写**，使用 `#` 后接空格的标准 Markdown 写法；不要把标题缩进成代码块。

## 程序迁移与验收

| 模式 | 用途 | 行为 |
| --- | --- | --- |
| 默认兼容模式 | 标题与历史引用迁移完成前维持现有调用 | 暂保旧法条特判、模糊匹配和固定 8 行兜底；不能作为新资料验收依据 |
| `--strict-headings` | 新资料和新引用验收 | 只用标题树和精确路径；缺失或多重命中报错，不回退到正文搜索 |

Python 调用显式传 `strict_headings=True`；CLI 示例：

```bash
PYTHONPATH=tech/chatflow/poc .venv/bin/python -m unittest test_source_format
.venv/bin/python tech/chatflow/poc/ground.py --node temporary-shelter --strict-headings
.venv/bin/python tech/chatflow/poc/wiki_update.py --strict-headings --fail-on-drift
```

第一条只检查可自动判断的 source 格式，不证明 PDF 顺序、疑似断行、复杂手册层级或
法律内容完整；这些仍须人工验收。后两条在新 wiki 生成后检查其实际引用。

历史 source 的标题和引用尚未全部迁移时，这些严格检查可能报错，这是待迁移清单，
不应通过删除引用或接受错误基线掩盖。先对照原文整理标题，再迁移 wiki 引用并逐条验收；
所有现有调用验证通过后，才能切换默认模式并删除旧抽取逻辑。程序迁移不会自动改动原始 source。

历史 `source_refs` 中还有只指向整份文档、没有 `#` 的引用。审计会将其列为错误；兼容模式加载节点时会明确警告并跳过该来源摘录，保留原先已加载的节点和其他有效摘录。严格模式不允许这样跳过，必须修正后再用。

## Q4：PDF 转 Markdown 需要什么后处理

### 总览：决策树

```
拿到一份 PDF 转出来的 Markdown
│
├─ ① 诊断：标题是否都在其内容之前？
│   │
│   ├─ 否（顺序错乱）
│   │    ├─ 还有原始 PDF → 按栏重新提取（治本）
│   │    ├─ 只需要少数几节 → 人工摘录（性价比最高）
│   │    └─ 法律附录部分 → 单独核对顺序和完整性，合格才保留
│   │
│   └─ 是（仅表层损伤）
│        └─ ② 删页眉 → ③ 隔离目录 → ④ 核对双语 → ⑤ 拆行 → ⑥ 标题分级
│
└─ ⑦ 验收：开头对、结尾不串、该有的小节都在
```

**最重要的是不要跳过 ①。** 顺序错乱的文件，②–⑥ 做得再干净也没用。

以下是各步骤的展开。

### 第 0 步：先诊断，不要直接洗

**判据一句话：**

> **每个小节标题，是否都出现在它自己的内容之前？**

打开文件，挑一大段，看开头和结尾：

| 顺序错乱的信号 | |
| --- | --- |
| 标题出现在本行很靠后的位置，而它的内容在前面 | ⚠️ |
| 段落以 `—`、`）`、`。` 等续接符号开头 | ⚠️ |
| 一行结尾的半句话，接的是本行开头 | ⚠️ |

### 两类损伤，对策不同

| | A 类：表层脏 | B 类：顺序乱 |
| --- | --- | --- |
| 症状 | 页眉、目录、整页一行、中英交错 | 标题与正文错位、段落回绕 |
| 脚本能修吗 | ✅ 能 | ❌ **不能** |
| 怎么办 | 走下面 5 步 | 见下方 |

**B 类（顺序乱）不要浪费时间写脚本**，三选一：

1. **还有原始 PDF** → 用 layout-aware 方式**按栏**重新提取（治本）
2. **只需要几节** → **人工摘录**那几节（性价比最高）
3. **法律附录部分** → 单独对照原文验收，顺序和内容完整才保留

> 之前的实测只证明特定文件的附录损伤较小，不能推导为“法条天然可用”。同一文件的正文和附录都需要独立验收；有条号也可能缺页或错序。

### A 类清洗步骤（顺序不能换）

| # | 步骤 | 为什么 |
| --- | --- | --- |
| 1 | 删页眉页脚 | 先删，否则干扰后续判断 |
| 2 | 隔离目录条目 | 保留人工清单，不把目录条目变成正文标题或引用锚点 |
| 3 | 核对双语段落 | 仅去除确认重复且无独有信息的外语译文，不因语言不同删除唯一正文 |
| 4 | 按结构拆行 | 在 `第X章`／`一、`／`（一）`／`第X条`／`1、` 前断行 |
| 5 | 按原文结构分级标题 | 法条、案例等可独立抽取单元也加标题；见「三条格式规则」 |

### 验收标准（三条全过才算完）

```
① 抽出的片段，开头就是该锚点自己的标题
② 结尾没有混进别的小节内容        ← 检查末尾 100 字
③ 你知道应该在里面的小节，确实都在  ← 必须人工判断
```

⚠️ **第 ③ 条只能人做**——机器不知道「危险评估」下面应该有三个危险等级。

⚠️ 只检查「两个不同锚点返回不同内容」**远远不够**：实测有文件通过了这条，但内容仍有 49% 是从别处串进来的。

## 附：引用必须可解析

`source_refs` 应声明完整的 `文件路径#标题路径`。引用审计会将漏写 `#`、空锚点或不存在的文件列为错误；不能悄悄不加载。严格模式还会拒绝非标题锚点和多重命中。历史无锚点引用的兼容警告仅用于迁移期，见上节。

```
❌ knowledge/source/某手册.md
✅ knowledge/source/某手册.md#第一章/第二十三条
```

写完引用请**实际跑一次**，确认真的抽到了内容。

## 一句话总结

> **保留编号和 `目录.md`；URL 放 frontmatter，图片内容转文字否则删除。所有独立抽取单元按原文结构加标题，用完整路径区分重名；新资料必须通过严格模式验收。PDF 先核对阅读顺序和完整性，再整理格式，不用猜测补齐原文。**
